## 9. Consolidate to one connection per page (post-implementation refinement)

- [x] 9.1 Raised after 8.3: the application-detail page opened two separate WebSocket connections (its own chat socket plus `main.js`'s page-wide notifications socket). Merged `NotificationConsumer`/`ChatConsumer` into a single `RealtimeConsumer` (see design.md D3) reachable at `/ws/updates/` (notifications only) or `/ws/updates/<application_id>/` (notifications + that application's chat); outgoing payloads now carry a `"kind"` field so a single `onmessage` handler can dispatch correctly
- [x] 9.2 `main.js` now skips opening its own notifications socket when `window.__mergedRealtimeSocket` is already set (by the chat page's inline script, which runs first in script load order); updated `apps/main/tests/test_consumers.py` and `test_realtime_broadcast.py` to the merged consumer/URLs; verified: 52/52 tests pass against live Redis, `ruff`/`djlint` clean, and a full `docker compose up --build` rebuild boots and serves correctly
- [x] 9.3 **Regression found and fixed**: the `!window.__mergedRealtimeSocket` guard in 9.2 wrapped the *entire* notifications block, including the one-time initial `updateNotificationsCount()` fetch — so on the chat page (which sets that flag), the navbar's notification count never rendered at all on page load, only updating later if a live push happened to arrive. Split the guard: the initial fetch now always runs when the notifications UI is present, independent of whether this page also opens its own socket; only the socket-opening itself is skipped when merged. Verified live in browser: count now shows correctly on the chat page immediately on load.
- [x] 9.4 Stopped re-fetching over HTTP on every push: `main.js`'s `incrementNotificationsCount()` bumps `#notifications-count` directly from the push (the WS event already tells us exactly one new notification exists); `view-application-job.html`'s `appendChatMessage()` appends the pushed chat payload directly to `#single-chat` instead of re-calling `fetchMessages()`. Both keep their one-time initial HTTP fetch for first render.
- [x] 9.5 Added `apps/main/tests/test_frontend_realtime.py`: two Playwright (browser) tests proving 9.4 — a real notification/chat write (via `services.py`, same path an HTTP view uses) updates the DOM through the WebSocket push with no second HTTP fetch to `/notifications-count/` or `/api/v1/chat-messages/<id>/`. Uses `channels.testing.ChannelsLiveServerTestCase` (plain `LiveServerTestCase` is WSGI-only, can't serve the WebSocket upgrade) against a real Daphne+Redis instance. Two blockers found and fixed along the way, not anticipated in design.md: (1) `ChannelsLiveServerTestCase` refuses an in-memory sqlite DB (this project's test-runner default) — added a `FILE_TEST_DB` env var (`jobPortal/settings/base.py`) that switches only this to a file-based sqlite test DB, gated so the rest of the suite's fast in-memory default is untouched; the test class itself `unittest.skipUnless`s on that var (and thus doesn't run, or fail, in a plain `manage.py test`). (2) Playwright's sync API keeps a running asyncio event loop on the calling thread, which both trips Django's `async_unsafe` ORM guard (worked around with `DJANGO_ALLOW_ASYNC_UNSAFE`) and makes `services.py`'s `_broadcast()` (`async_to_sync`) raise outright — fixed by running the test's write-path calls (`services.create_notification`/`post_conversation_message`) on a plain background thread, which also matches how a real HTTP request's write actually runs (never on the browser-driving thread). Verified: both new tests pass against live Redis; full suite still 54/54 (52 pass + 2 skipped by default); `ruff check`/`ruff format --check` clean.
